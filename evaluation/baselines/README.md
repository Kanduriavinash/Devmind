# Repair baseline evaluation status

`run_comparison` now runs the unmodified test suite once per issue as a shared preflight, then applies the same candidate-validation procedure to all three conditions: LLM-only, one-shot RAG, and iterative DevMind. Every valid one-shot patch is sent to the Docker-only sandbox; the iterative arm uses that sandbox for each bounded attempt and records its final candidate test result. A missing Docker image or unavailable engine is recorded as blocked, never as a pass. No source repository is modified by the sandbox.

The runner uses one provider/model object and records the shared baseline test outcome, actual provider calls, total prompt characters and a whitespace-token estimate, test-runner name, timeout setting, retrieval top-k, patch-context character budget, sandbox calls, status, test output, and latency. Summary output includes baseline test pass rate with its observed denominator and blocked count. The task conditions intentionally differ in retrieval context and retry behavior. The one-shot conditions receive one generation request; iterative DevMind may make up to the configured attempt limit. To claim a fair repair comparison, also pin identical issue revisions, model version/parameters, relevant context budgets, test environment/image, timeout, and final grading protocol. Those configuration fields and the issue-level base commit/snapshot validation need to be added or checked before real comparative runs.

The dataset contains no adjudicated issue-resolution labels and the runner has not completed an actual same-issue study. It is therefore a testable, more comparable execution framework, not evidence that one strategy performs better. Preserve every patch and sandbox output. Do not count retries as resolved issues or interpret selected-test success as confirmed issue resolution.
